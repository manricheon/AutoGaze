# 셀렉터 튜닝 가이드 — 생성-후-심판(LLM judge) 프레임워크

다른 머신/다른 모델에서 "셀렉터 → VLM 비디오 설명 생성 → 강한 모델 심판"
방식으로 파라미터를 튜닝할 때 그대로 따라 할 수 있는 절차. v0.8 라운드
(2026-07 말)에서 실증된 프로토콜이며, 세부 근거는 `v08-prereg.md`와
`design.md`의 해당 라운드 기록 참조.

## 0. 원리 (왜 이렇게 하나)

- **프록시(NLL, 임베딩 유사도)는 승자 선정에 쓰지 않는다.** v0.8 라운드에서
  NLL 순위와 심판 순위가 dev·holdout 양쪽에서 불일치함이 실증됐다. 프록시는
  탈락 스크린(명백히 나쁜 구성 걸러내기)까지만.
- **정답(GT) 캡션이 없어도 된다.** 클립당 동결된 8프레임이 곧 GT다. 심판은
  프레임만 보고 두 캡션을 비교한다. dense 캡션을 참조로 쓰면 생성 모델
  자신의 환각이 기준이 되는 순환이 생기므로 금지.
- **쌍대 비교가 헤드라인이다.** (a) 후보 vs random@동일비율 = 주 판정,
  (b) 후보 vs dense = 정보 손실 측정. 절대 점수는 쓰지 않는다.

## 1. 준비물

1. **클립 풀**: 수백~1천 개의 짧은 클립(수 초). 도메인이 실서비스와 유사할 것.
2. **평가셋 분리**: dev-N(개발·후보 선정)과 holdout-M(최종 1회 판정)을
   서로소로 층화 추출(모션 세기 분위 × 장면 임베딩 클러스터). 시드 고정,
   목록을 저장소에 커밋. holdout은 **집계를 단 1회만** 한다.
3. **프레임 동결**: 클립당 8프레임(균일+처음/끝, 타임스탬프 포함)을 JPEG로
   1회 추출하고 sha256을 커밋. 이후 절대 재인코딩하지 않는다.
   (`scripts/make_evalset_manifest.py` 참조)
4. **사전 등록 문서**: 스윕 그리드, 탈락 규칙, 승자 규칙, 성공 기준을
   실행 **전에** 커밋. 도중 변경은 전부 수정 기록(A1, A2, ...)으로 남긴다.

## 2. 생성 (실서비스 모델로)

구성별로 같은 클립에 캡션을 생성해 `captions.json`으로 저장한다. 형식:

```json
[
  {"clip": "xxx.mp4",
   "dense": "<전체 토큰 캡션>",
   "<spec-A>@0.25": "<캡션>", "<spec-A>@0.5": "<캡션>",
   "random@0.25": "<캡션>", ...},
  ...
]
```

- **디코딩을 라운드 내내 고정**하라(greedy 권장, 온도/시드 포함). 같은 설정
  2회 실행 캡션 동일률을 5클립으로 먼저 확인(≥90% 권장).
- **random 대조군 필수**(동일 keep 비율의 무작위 선택), dense 상한 필수.
- 입력 스케일 함정: 프로세서가 rescale을 이중 적용하면 모델이 검은 영상을
  보면서도 그럴듯한 수치를 낸다. **pixel_values 표준편차 tripwire**
  (std < 0.05면 즉시 예외)를 반드시 넣어라. v0.8 라운드에서 이 버그가
  프록시 지표로는 전혀 안 잡히고 심판 QC로만 잡혔다.
- 이 저장소 기준: `scripts/eval_mllm_attach.py --generate --kv-cache
  --clips-file <dev.txt> --configs "<spec;spec;...>" --ratios 0.25,0.5`.
  회사 모델이면 자체 파이프라인으로 같은 형식의 captions.json만 만들면 된다.

## 3. 심판 하네스

### 3.1 작업 생성
`scripts/eval_caption_judge.py prepare --captions captions.json
--specs "<spec;...>" --ratios 0.25,0.5 --jobs jobs.jsonl`
→ 클립×쌍×순서(A/B 스왑 2회)마다 1 job. job에는 프레임 경로와 심판
프롬프트(아래 규칙 포함)가 들어간다.

### 3.2 심판 프롬프트 핵심 규칙 (그대로 복사 권장)
- 8프레임이 곧 GT. 프레임에서 검증 불가한 주장은 환각으로 **감점**.
- 길이·문체·화려한 디테일에 가점 금지. 짧고 정확한 쪽이 이긴다.
- 5축(objects/actions/scene/temporal/hallucination) + overall, 각각
  "A|B|tie". 출력은 STRICT JSON.

### 3.3 심판 자체 검증 (본 채점 전 필수, 20클립)
① dense가 random@0.10을 승률 ≥80%로 이겨야 함 ② 타 클립 캡션 스왑은
≥90% 잡아내야 함 ③ 문장 셔플 dense는 temporal에서 패배 ④ 순서 스왑
자기일치 ≥80% ⑤ 장황 패딩 캡션이 간결 dense를 못 이겨야 함.
하나라도 실패 → 프롬프트 수정 후 재검증. 통과 전 본 채점 금지.

### 3.4 심판 실행
- 심판 모델은 생성 모델보다 강한 멀티모달 모델이면 무엇이든 됨(Claude,
  Gemini 등). `eval_caption_judge.py`에 gemini / gemini-cli 백엔드 있음.
- 판정은 `{"id","axes":{...5축...},"overall","reason"}` JSONL로 수집.
  **overall은 최상위 키**(에이전트가 axes 안에 넣는 실수가 실제로 나옴 —
  수집기에서 자동 복구 로직을 두면 편함).
- dev는 스왑 2회 1세트, holdout은 **독립 3반복**(같은 job을 3번, 반복 간
  컨텍스트 공유 금지).

### 3.5 집계 (사전 등록된 규칙)
- 비교 키 = (tag, clip, first, second, ratio).
- 순서 스왑 2판정이 일치하면 그 결과, 불일치면 tie(자리 편향 제거).
- holdout: 반복별 위 결과를 3반복 다수결(2/3 미만이면 tie).
- 후보별 vs-random 승/무/패, 승률 + Wilson 95% CI, 부호검정(양측,
  tie 제외), vs-dense 패배율.
- **QC 게이트**: 순서 스왑 일치율 보고(참고: 0.25에서 ~75-80%, 0.5에서
  ~70% 수준이 정상), 캡션 길이차-승패 상관 r > 0.4면 심판 오염으로 간주,
  vs-random tie율 > 40%면 그 ratio는 헤드라인에서 제외(사전 등록 폴백).

## 4. 라운드 구조 (깔때기)

1. **Stage A** (dev 부분집합, 프록시): 그리드 전체를 싼 지표로 돌려
   **명백 열세만 탈락**(기본 대비 노이즈 1σ 초과 열세). 승자 선정 금지.
2. **Stage B** (dev 전체, 심판): 생존 후보 + 기본 + random. 승자 규칙은
   사전 등록 — v0.8에서 쓴 규칙: ① 양 ratio 모두 vs-random p<0.05 승리
   게이트 → ② min(승률@0.25, 승률@0.5) 최대 → ③ ±2%p 동률 시 평균
   vs-dense 패배율 최소.
3. **Stage C** (holdout, 심판 3반복): 승자 + 기본 + random만. **집계 1회.**
   성공 기준(사전 등록): 승자가 random을 유의하게 이기고 vs-dense 손실이
   기본 대비 악화되지 않을 것. 결과가 무엇이든 재방문 금지(winner's curse).

## 5. 함정 목록 (v0.8 라운드에서 실제로 겪은 것)

- **자기일관 폐루프**: 캡션과 NLL을 같은 손상 입력에서 만들면 입력이
  망가져도 그럴듯한 델타가 나온다. 프레임 근거 심판만이 이를 잡는다.
- **픽셀 마스킹 스크린의 한계**: 드롭 패치를 어둡게 칠한 프레임을 사람/VLM이
  보고 평가하는 방식은 셀렉터-vs-random 구분(버그 탐지)에는 강하지만,
  구성 간 순위는 실제 토큰 드롭과 **부호가 뒤집힐 수 있다**(실측 Spearman
  -0.8). 저예산 sanity check 전용.
- **dev 타이브레이크는 뒤집힌다**: dev에서 박빙(±2%p)이면 holdout에서
  순위가 바뀔 수 있다(실제로 바뀜). 박빙 후보는 버리지 말고 holdout에
  관찰 arm으로 실어 보내되, 관찰 arm으로 당회차 결정을 바꾸지 않는다고
  미리 등록하라.
- **정성 확인 병행**: `scripts/make_qual_report.py`로 선택 오버레이 +
  캡션 대조 + 판정 사유를 한 HTML로 뽑아 눈으로 확인. 이식 검증(다른
  머신에서 파라미터 실수)에도 이걸 쓰면 된다 — 오버레이는 리포트 생성
  시점에 실제 셀렉터를 돌려 그린다.

## 6. 규모·비용 감각 (v0.8 실측)

- dev-60 1회전 = 캡션 360개(KV캐시 greedy, M-시리즈 Mac에서 ~6h) +
  판정 1,080건(순서 스왑 포함).
- holdout-120 3반복 = 캡션 840개(~14h) + 판정 7,200건.
- dev-60은 승률 ≥67% 효과를 검출(α=0.05, power 0.8), holdout-120의
  95% CI 폭은 대략 ±9%p.
